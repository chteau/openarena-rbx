# Bots: notes

The bots are a Luau port of ioquake3's botlib (`vendor/ioq3/code/botlib`)
and of OpenArena's bot AI (`vendor/gamecode/code/game/ai_*.c`), in Quake
units and axes like the rest of the game code. Bots think through the
same interfaces as in C: the AI asks botlib for routes, goals and moves,
botlib turns them into a `bot_input_t`, the AI converts it to a
`usercmd_t` (`BotInputToUserCommand`) and hands it to the engine with
`trap_BotUserCommand`, which runs `SV_ClientThink` and the normal server
pmove, exactly like a client's command.

## Layout (`src/server/bot/`)

| Path | What |
|---|---|
| `botlib/b_local.luau` | botlib namespace `B` (every non-static botlib function and global) |
| `botlib/consts.luau`, `botlib/structs.luau` | generated (`tools/gen_bot_defs.py`) from ioquake3's `q_shared.h`, `surfaceflags.h`, `botlib/*.h` and the structs in `botlib/*.c` |
| `botlib/l_*.luau`, `botlib/be_*.luau` | one module per C file, or `_1.._n` parts of one C file sharing its statics through `B.FileStatics("<file>")` |
| `botlib/botlib.luau` | loads every botlib file, returns `B` (`B.GetBotLibAPI`) |
| `sv_bot.luau` | port of `server/sv_bot.c`: botlib import, `SV_BotFrame`, console messages, snapshot entities, `BOTLIB_USER_COMMAND` |
| `BotGame.luau` | the adapter between `sv_bot.luau` and the server engine (below) |
| `g_botlib.luau` | the game's botlib traps (`trap_BotLib*`, `trap_AAS_*`, `trap_EA_*`, `trap_Bot*`, ...), generated by `tools/gen_g_botlib.py` from `g_syscalls.c` and `sv_game.c` |
| `ai_defs.luau`, `ai_consts.luau`, `ai_structs.luau` | the AI's constants (game `g_defs` plus the bot headers) and structs (`bot_state_t` & co. over `g_structs`) |
| `ai_main_*.luau` ... `ai_vcmd.luau` | port of `ai_main.c`, `ai_dmq3.c`, `ai_dmnet.c`, `ai_team.c`, `ai_chat.c`, `ai_cmd.c`, `ai_vcmd.c` into the game namespace `G` |
| `Bots.luau` | entry point: `Install`, `InitGameProgs`, `Frame`, blob helpers |

`g_bot.c` (addbot, `bot_minplayers`, bot info, the bot queue) is part of
the game module and is ported on feat/game (`src/server/g_bot.luau`); it
calls the AI through the same `G.BotAISetupClient`, `G.trap_AAS_Initialized`
... names that `Bots.Install` provides.

## Wiring it into the server (what feat/game needs to do)

1. Load the game module as now (`Game.luau`), then install the bots:

   ```lua
   local Bots = require("./bot/Bots")
   Bots.Install(require("./bot/BotGame").FromEngine({
       SV = SV, W = require("./sv/sv_world"), Cvar = Cvar, Fs = Fs,
       Collision = require("../shared/Collision"), G = G, C = C,
       structs = require("../shared/structs"),
   }))
   ```

   `Install` loads the AI and `g_botlib` into `G` (replacing every function
   of `ai_stubs.luau`, which can then be deleted), and runs
   `SV_BotInitCvars` + `SV_BotInitBotLib` as ioquake3's `SV_Init` does.
2. Call `Bots.InitGameProgs()` where ioquake3's `SV_InitGameProgs` latches
   `bot_enable` (before the game module's `GAME_INIT`).
3. Call `Bots.Frame(sv.time)` where ioquake3 calls `SV_BotFrame`: in
   `SV_Frame` before the `GAME_RUN_FRAME` loop (dedicated server), and after
   each of `SV_SpawnServer`'s settle frames (`GAME_RUN_FRAME` x3 for bots
   that survive a map change, then once more).
4. Mount the botfiles: `Bots.MountBotfiles(blob, Fs.Mount)`, where `blob`
   is the `Botfiles` buffer blob from `tools/pack-botfiles.py` (joined with
   `Bots.JoinBlob`, same index/chunk format as the converter's blobs), and
   mount each map's `.aas` as `maps/<map>.aas` (the converter's `Aas` blob,
   joined). The map's `.bsp` checksum must reach `sv_mapChecksum`
   (`lumps.checksum` in `SV_SpawnServer`): botlib checks it against the
   `.aas` header and refuses an out-of-date file. The converter does not
   ship it yet; `tests/bots/md4.luau` is `Com_BlockChecksum` (MD4) and gives
   the oracle's values (oa_dm1 1737490240, oa_ctf2 -967542298, am_thornish
   1384519091, oa_bases7 600114830), so either the converter writes it into
   `map.json` or the server computes it where it still has the BSP bytes.

### The BotGame adapter surface

`BotGame.FromEngine` builds it from the modules above; another host can
fill the same table by hand. Fields (ioquake3 semantics throughout):

| Field | ioquake3 |
|---|---|
| `Com_Printf(text)`, `Com_Error(level, text)`, `Sys_Milliseconds()` | console / clock |
| `Cvar_Get(name, value, flags)`, `Cvar_VariableIntegerValue(name)`, `Cvar_VariableString(name)` | cvars |
| `FS_ReadFile(path) -> buffer?` | whole-file reads for `botfiles/*` and `maps/*.aas` |
| `trace_t()` | a zeroed `trace_t` |
| `SV_Trace`, `SV_ClipToEntity`, `SV_PointContents`, `SV_inPVS` | `sv_world.c` (botlib's `passent -1` is passed as `ENTITYNUM_NONE`) |
| `CM_EntityString`, `CM_InlineModel`, `CM_ModelBounds` | collision model |
| `GetClient(n)` | `&svs.clients[n]` (`reliableCommands/Sequence/Acknowledge`, `frames[]`, `outgoingSequence`, `lastPacketTime`, `lastUsercmd`, `gentity`) |
| `svsTime()`, `MAX_RELIABLE_COMMANDS`, `PACKET_MASK` | `svs.time`, constants |
| `SnapshotEntityNumber(frame, i)` | number of the i-th entity of a client snapshot frame |
| `SV_ClientThink(n, cmd)`, `SV_ExecuteClientCommand(n, s, clientOK)` | bot user commands and bot client commands |
| `GameRunning()`, `VM_Call_BotAIStartFrame(time)` | `gvm`, `VM_Call(gvm, BOTAI_START_FRAME, time)` |

Bots must get their snapshots built every frame (the engine already does
it in `SV_SendClientSnapshot` for `SVF_BOT` clients), since
`trap_BotGetSnapshotEntity` reads them.

## Porting conventions that cross module boundaries

- **Out-parameters.** A scalar or string a C function writes through a
  pointer (`int *`, `float *`, `char *buf`) is dropped from the Luau
  parameter list and returned after the C return value:
  `local ok, value = G.trap_AAS_ValueForBSPEpairKey(ent, key, size)`. Structs,
  vectors and arrays are tables filled in place. A function that returns the
  buffer it fills (`ClientName`) returns the string once. Both botlib and the
  AI follow this, which is why the traps are plain pass-throughs.
- Struct fields named after Luau keywords get `_` (`reach.end_`).
- botlib uses ioquake3's `VectorNormalize` (`Q.VectorNormalizeIoq3`), which
  rounds differently from OpenArena's.
- The be_aas_* files compute in float32 (`Q.f`) like the C, so routing and
  prediction match the native botlib bit for bit.

## What is deliberately not ported

- **Reachability and cluster calculation** (`be_aas_reach.c` beyond its
  runtime queries, `be_aas_cluster.c` beyond `AAS_InitClustering`'s early
  return, `be_aas_optimize.c`): every OpenArena map ships an `.aas` with
  reachabilities and clusters, so botlib never computes them unless
  `bot_forcereachability`/`bot_forceclustering` is set. With those set,
  the port prints an error and keeps the file's data. `AAS_Optimize` and
  `AAS_WriteAASFile` only run when botlib saves an `.aas`; there is no
  writable file system, so the write fails as C does when the file can't
  be opened.
- **Route cache files** (`bot_saveroutingcache`, `maps/*.rcd`): none ship,
  and none can be written; reading finds no file and computes, as in C.
- `l_crc.c` is only used by the route cache files.
- `l_log.c` keeps the log in memory (no files).
- `l_memory.c`: Luau's garbage collector replaces the zone/hunk; the
  allocation functions become table constructors at each call site.

Maps without an `.aas` (`islandctf`): `BotLibLoadMap` fails with botlib's
own "can't open maps/islandctf.aas" error, `trap_AAS_Initialized` stays
false and `G_AddBot`/`G_CheckMinimumPlayers` refuse bots, as in OpenArena.

## Verification

- `tools/oracle-bots/build.sh` compiles ioquake3's botlib and collision
  model natively (`build/oracle-bots/oracle-bots`, not committed) with a
  minimal botlib import, and extracts oa_dm1, oa_ctf2, am_thornish and
  oa_bases7 (`.bsp` + `.aas`) and the botfiles from the pk3s.
- `tools/bots-overlay.sh` lays this branch over the feat/game worktree in
  `build/overlay` (until the branches merge); `tools/sync-overlay.sh`
  refreshes it after edits.
- `cd build/overlay && lune run tests/bots/oracle_aas.luau` replays the
  oracle on the four maps and diffs bit for bit: the info line (BSP
  checksum, areas, reachabilities, clusters, portals), the whole
  reachability list, `AAS_PointAreaNum` for 2000 random points,
  `AAS_AreaRouteToGoalArea`/`AAS_AreaTravelTimeToGoalArea` for 2000 random
  area pairs and travel-flag sets, 2000 `AAS_TraceClientBBox` traces and 500
  `AAS_PredictClientMovement` runs.
- `tools/check_bots.sh [--strict] <files>`: load, member and name checks
  plus luau-lsp lint.
- `cd build/overlay && lune run tests/bots/sim.luau <map> <bots> <seconds> [g_gametype]`:
  a headless match through the game branch's server (its pmove, items,
  weapons), maps' `.aas` taken from the converter's `Aas` blob modules and
  the botfiles from the `Botfiles` blob. It counts per bot the items picked
  up ("Item:" log lines), distance, jump pad (`EV_JUMP_PAD`) and teleporter
  (`TeleportPlayer`) uses, shots (`EV_FIRE_WEAPON`), kills and deaths, and
  times `SV_BotFrame` (all bots' thinking, botlib included).

### Results (lune, this machine, 50 ms frames)

| Run | Bots | ms per bot per frame | server ms per frame |
|---|---|---|---|
| oa_dm1 FFA, 120 s | 4: 20-29 items, 29-31k units walked, 57-91 shots, 4-9 kills each | 0.59 | 2.9 |
| kaos2 FFA, 120 s | 4: 26-35 items, 1-4 jump pads and 1-4 teleports each | 0.85 | 4.2 |
| oa_ctf2, every g_gametype 1, 3-12, 60 s | 4, no script errors | 0.54-0.91 | 2.7-4.3 |

oa_dm1 has one teleporter and no jump pad; in 120 s of fighting the bots
did not route through the teleporter, which is why kaos2 is the jump pad
and teleporter evidence. The game-type runs show the AI runs in every OA
mode without errors; whether each mode's team strategy (flag runs, obelisk
attacks, cube delivery, domination points) plays like native OA has not
been compared against a native OpenArena run.

## Generator note for feat/game

`tools/gen_consts.py`'s evaluator rejects a macro body that contains a tab,
which a `\` continuation line leaves behind, so multi-line macros such as
`TFL_DEFAULT` are dropped. `tools/gen_bot_defs.py` patches that locally;
the same fix would apply in `gen_consts.py` itself.
